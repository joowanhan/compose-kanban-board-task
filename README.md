## 기능 요구 사항

- [x] 1단계 피드백 반영
    - [x] Modifier
        - [x] Modifier 주입
            - 컴포저블 함수가 외부로부터 Modifier 객체를 매개변수로 전달받아 내부의 최상위(Root) 레이아웃에 적용하는 설계 패턴 적용
            - 재사용성과 유연성 극대화: 컴포넌트를 호출하는 상위 계층(부모)에서 해당 컴포넌트의를 자유롭게 제어할 수 있어야 한다. 내부에 Modifier가
              하드코딩되어 있으면, 다른 화면에서 이 카드를 클릭 가능하게 만들거나 외부 여백을 다르게 주고 싶을 때 기존 코드를 수정하거나 새로운 컴포넌트를 만들어야
              하는 문제가 발생한다.
            - 책임의 분리: 부모 컴포저블은 자식 컴포저블이 '어디에, 어느 정도 크기로 배치될지(Layout)'를 결정하고, 자식 컴포저블은 '자신의 내부를 어떻게
              그릴지(Drawing)'를 결정하게 한다.
            - 기본값으로 빈 Modifier를 할당하여, 외부에서 주입하지 않아도 정상 동작하도록 만든다.
            - 컴포즈의 Modifier 주입 기본 원칙: 주입받은 Modifier는 오직 '최상위 요소'에만 한 번 적용해야 한다. 내부의 자식들은 각자의 고유한 속성을
              갖기 위해 빈 상태의 Modifier에서 새롭게 시작해야 한다.
                - 이유: 만약 자식 요소들에도 주입받은 modifier를 체이닝해서 사용하면 외부에서 의도한 설정이 내부 자식들에게 의도치 않게 중복 적용될 수 있기
                  때문

            - [x] Cadr의 Modifier에서 width()와 padding() 순서 변경
                - 디자인 시안이 요구하는 카드의 '전체 크기'를 알맞게 맞춘 구조
                - UI 컴포넌트를 설계할 때는 항상 **"전체 구조와 제약을 먼저 설정하고, 세부적인 내부 여백과 스타일을 나중에 깎아나간다"**는 규칙을 따라야 함
        - [x] Named arguments 활용
            - 패딩 값에 positional argument가 사용된 것 등을 리팩토링
    - [x] 가시성 제한

## 프로그래밍 요구 사항

단위 테스트만으로도 충분한 로직과, UI 테스트가 필요한 영역을 구분한다.
핵심 비즈니스 로직을 가지는 객체를 분리해 단위 테스트를 진행한다.
Compose UI Testing을 활용하여 1단계의 기능 요구 사항을 테스트한다.
